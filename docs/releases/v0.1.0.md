## Release notes

Court Legacy v0.1.0 is the first explicitly tag-ready release baseline. Phase18 focuses on release safety rather than new gameplay rules.

- Installable PWA metadata and controlled service-worker updates are available without caching authenticated API/session traffic.
- Existing schema-v8 saves migrate to the current schema-v9 format when loaded; PWA startup itself does not mutate the save payload.
- Phase21 adds persisted player relationship bonds and related migration data while preserving v8 load compatibility through the v8→v9 migration path.
- Deterministic 1/10/30-season soak tooling captures invariant and balance evidence for release seeds.
- Critical browser contracts cover onboarding, saving/reload, training and week progression, lineup interaction, official tournaments, year rollover, and continued play.
- PvP browser coverage preserves server authority, opponent privacy boundaries, and same-command-id retry/idempotency behavior after ambiguous responses.
- Accessibility release coverage includes accessible names, keyboard focus, dialog focus trapping/restoration, practical 44px touch targets, text status feedback, and reduced motion.
- Ordinary feature-branch pushes no longer run full GitHub Actions CI. Required CI runs on pull requests and `main`, with stale PR runs cancelled, reducing duplicate failure notifications.

The Phase18 release foundation itself did not change gameplay simulation, balancing rules, PvP authority, or persisted save shape. Phase21 later advances the persisted save schema from v8 to v9 for relationship persistence.

## Known issues

- In 30-season release-seed samples, the user school can materially exceed CPU p90 strength. Phase19 will address CPU/school-strength progression and long-run competitive balance.
- Neither 30-season release seed reached facility Lv50. Phase19 will review facility/economy progression pacing rather than forcing a late Phase18 numerical change.

## Rollback procedure

Pre-PR18-4 known-good source SHA:

`2f21c00b40bda57019b322a90e119d7e92aa2c3b`

If a v0.1.0 deployment must be rolled back:

1. Identify the exact deployed v0.1.0 SHA and preserve its CI/release evidence.
2. Check out the known-good source SHA above, or the latest explicitly approved known-good SHA if a later hotfix baseline has been recorded.
3. Keep the same production Supabase configuration and secrets.
4. Build and redeploy that source using the normal Cloudflare deployment path.
5. Do **not** destructively reverse existing Supabase migrations merely to roll back source code.
6. Confirm login/bootstrap, an appropriate save-loading path for the rollback target, a normal game action/save, and the critical PvP path after redeploy.

The current release writes schema-v9 saves. A pre-v9 source build is not expected to load snapshots already written as v9, so preserve v9 snapshots before any rollback and use a forward hotfix or an explicitly designed down-migration if v9 save continuity is required.

## Tagging procedure

Create the public tag only after every required gate is GREEN:

1. Merge PR18-4 into `main`.
2. Record the exact merge SHA.
3. Confirm the automatic `main` CI for that SHA is fully GREEN.
4. Manually dispatch the `Release Gate` workflow on that exact `main` SHA/ref.
5. Confirm dependency audit, release metadata, repository verification, smoke soak, long soak, and full mobile E2E are all GREEN.
6. Create tag `v0.1.0` from that exact verified `main` SHA.
7. Create the GitHub Release from `v0.1.0` using this document as the release decision record.

Do not move an existing `v0.1.0` tag to a different commit. If a release candidate fails after tagging, follow the rollback/hotfix process and issue a new version rather than rewriting release history.
