# Court Legacy V2 全面刷新設計

## 1. 目的

`Court Legacy` を、男子高校バレー部の監督として世代交代を何十年・何百年でも続けられるオンライン対応の育成シミュレーションへ再構築する。

V2では、キャラクター画像を中心にした見せ方ではなく、次の4点をゲームの核にする。

1. 毎年変化する新入生と世代交代
2. 学校評判と育成環境による長期成長
3. 選手ごとの差が大きい育成・編成・試合
4. 他プレイヤーの学校と戦う非同期PvP

既存実装は全面的に見直し、V2の目的に寄与しないUI・アート・保存機構・固定キャラクター要素は削除する。

---

## 2. プロダクト原則

### 2.1 永続的に遊べる高校バレー監督ゲーム

- 舞台は高校男子バレー。
- 1選手は原則3年間在籍する。
- 毎年度、3年生が卒業し、新1年生が入学する。
- 学校・監督・歴代記録は継続する。
- 年数上限は設けない。
- プレイヤーは「次の世代をどう育てるか」を繰り返し判断する。

### 2.2 新入生が最大のコンテンツ

毎年の新入生は単純なランダム生成にしない。

新入生の質・人数・タイプ・潜在能力は以下から算出する。

- 学校評判
- 直近の大会成績
- 全国大会実績
- スカウトネットワーク
- 練習設備
- 寮
- OB会
- 監督のスカウト能力
- 監督の育成実績
- 地域補正
- 年度ごとのランダム変動

強豪化するほど有力選手を獲得しやすくなるが、強豪校でも毎年必ず天才が来る仕様にはしない。

### 2.3 情報量は多く、操作は分かりやすく

Football ManagerやBasketball GMのように情報量を持たせつつ、日本のスマホゲームとして迷わない操作導線にする。

- 重要情報をカード化
- 一覧は表・数値・タグ中心
- 選手画像は必須にしない
- 画像読み込み完了を待たないと操作できない構造は禁止
- 主要操作は1〜2タップで到達
- PCとスマホの両方に対応

### 2.4 「動いているか分からない」状態を禁止

以下は禁止する。

- 白画面のまま待たせる
- 全画面ローディングだけを長時間表示する
- ボタン押下後に無反応に見える
- 保存状態が不明
- 通信エラー後に無言で元画面へ戻る

非同期処理では必ず状態を表示する。

例:

- `保存中…`
- `保存済み ✓`
- `対戦相手を取得中…`
- `試合データ作成中…`
- `試合結果を保存中…`
- `通信に失敗しました。再試行できます`

可能な限り、画面全体をブロックせず局所ローディングを使用する。

## 3. 既存コードの扱い

### 3.1 原則残すドメインロジック

以下はV2でも再利用価値があるため、テストを追加した上で原則残す。

- `src/domain/match/`
- `src/domain/calendar/`
- `src/domain/generation/`
- `src/domain/training/`
- `src/domain/team/`
- `src/domain/random/`
- `src/domain/world/`
- 学校評判・施設・試合・世代交代に関する純粋なドメインロジック

ただし、未使用コードやV2要件と競合する処理は削除する。既存インターフェースの互換維持は要件とせず、V2データモデルに合わせて整理・分割する。

### 3.2 削除するもの

V2では以下を削除する。

- `src/assets/characters/`
- `src/assets/player-parts/`
- `src/ui/player-art/`
- 固定4選手を中心にした専用キャラクターアート
- 表情差分、全身差分、SD差分
- 一般選手アトラス
- 画像ロード状態にUIが依存する仕組み
- `FeaturedPlayerHero` など固定キャラクター前提のUI
- `characterWorld`
- `playerAppearance`
- `playerArtRecipe`
- キャラクター画像中心の専用ドキュメント

削除後に参照が残らないことをTypeScript、ESLint、テストで検証する。

### 3.3 ローカル3スロット保存の廃止

IndexedDBの3スロット保存は、V2のメインセーブ方式として廃止する。

ローカル保存は以下に限定する。

- 一時キャッシュ
- 通信失敗時の復旧用データ
- UI設定

正式データはアカウントに紐づけてクラウドへ保存する。

## 4. 技術構成

### 4.1 フロントエンド

- React 19
- TypeScript
- Vite
- 既存Cloudflareデプロイ構成を維持

### 4.2 API

Cloudflare WorkerをAPI境界として使用する。

フロントからDBへ直接ゲーム更新を書き込まず、重要なゲーム更新はWorker経由で行う。

対象:

- セーブ更新
- 年度進行
- アイテム使用
- PvP対戦開始
- PvP結果確定
- ランキング更新
- ショップ購入

### 4.3 認証・DB

Supabaseを利用する。

- Supabase Auth
- PostgreSQL
- Googleログイン
- メールアドレスログイン

ゲストプレイは提供しない。

### 4.4 サーバー権威

PvP、ランキング、ショップ、アイテム、クラウドセーブはサーバー側を正とする。

クライアントから以下を信用しない。

- 所持アイテム数
- PvP勝敗
- ランキングポイント
- 選手能力の任意更新
- 通貨残高
- 購入済み状態

## 5. アカウント

### 5.1 起動フロー

未ログイン状態ではゲーム本編へ入れない。

1. タイトル
2. Googleログインまたはメールログイン
3. 初回のみ監督名・学校名設定
4. 初期学校生成
5. ホームへ遷移

### 5.2 1アカウント1本編セーブ

V2初期版では複数セーブスロットを提供しない。

- 1アカウントにつき1校
- 学校は長期継続
- データ消去は設定画面から明示操作

これによりPvP・ランキング・課金アイテムの整合性を簡潔に保つ。

## 6. 年間ゲームサイクル

### 6.1 1年度

基本サイクルは以下とする。

- 4月: 新入生加入
- 春: チーム形成・練習試合
- 初夏: インターハイ予選
- 夏: 合宿・育成
- 秋: 秋季大会・練習試合
- 冬: 春高予選
- 1月: 春高本大会
- 2〜3月: 次年度準備・スカウト
- 3月末: 3年生卒業
- 4月: 次年度へ

### 6.2 進行単位

基本進行は週単位を維持する。

毎週必ず大量の選択を要求せず、通常週は短時間で処理できる。

重要週のみ選択を増やす。

- 大会
- 新入生
- スカウト
- 合宿
- 怪我
- 進路
- チーム内イベント

## 7. 学校評判

### 7.1 表示ランク

評判ポイントを内部値として持ち、UIでは以下のランクを表示する。

- E: 無名
- D: 地区レベル
- C: 県大会常連
- B: 県内強豪
- A: 全国出場級
- S: 全国常連
- SS: 全国名門

### 7.2 評判増減

上昇:

- 県大会上位
- 全国大会出場
- 全国大会上位
- 全国優勝
- 強豪校撃破
- 有名選手の輩出
- PvP上位実績の一部

下降:

- 長期低迷
- 県大会早期敗退が続く

一度名門化した学校が1敗で急落しないよう、短期変動と長期実績を分離する。

## 8. 新入生・スカウトV2

### 8.1 入学人数

標準4〜8人。

学校の状況によって増減する。

### 8.2 選手クラス

内部クラスは以下とする。

- `normal`
- `promising`
- `elite`
- `generational`
- `monster`

UIでは内部名をそのまま見せず、スカウト評価・星・コメントで表現する。

### 8.3 出現イメージ

固定周期ではなく確率ベースにする。

- 一般: 毎年多数
- 有望: 毎年数名
- 大型新人: 数年に1人程度
- 天才: 5〜10年に1人程度の世界全体期待値
- 怪物: 15〜30年に1人程度の世界全体期待値

天才・怪物は自校に来るとは限らない。

### 8.4 評判による獲得確率

強い選手ほど高評判校を希望しやすい。

ただし100%固定にはせず、以下を加味する。

- 出身地域
- 監督の育成力
- 監督との相性
- ポジション競争
- 寮
- スカウト担当
- 学校の直近成績
- ランダム要素

### 8.5 スカウト段階では能力を完全公開しない

表示:

- 身長
- ポジション
- 利き手
- 中学実績
- スカウト評価
- 推定能力帯
- 推定将来性
- 特徴コメント

非表示または曖昧表示:

- 正確な潜在能力
- 一部性格
- 隠し特性
- 成長ピーク
- 怪我耐性

観察力・スカウト施設により情報精度が上がる。

## 12. 非同期PvP

### 12.1 基本方式

リアルタイムPvPはV2初期版では実装しない。

非同期PvPのみ実装する。

対戦相手がログインしていなくても挑戦できる。

### 12.2 チームスナップショット

PvP用にサーバーへチームスナップショットを保存する。

含む情報:

- 学校ID
- 学校表示名
- 監督表示名
- 選手能力
- 特性
- コンディション用PvP補正値
- スタメン
- ローテーション
- 戦術
- チーム戦力
- 評判
- PvPレーティング
- スナップショットバージョン

通常育成データそのものを相手へ公開しない。

### 12.3 マッチング

候補抽出に以下を使う。

- PvP Rating
- 直近PvP成績
- チーム戦力
- 学校評判

極端な格差マッチを避ける。

### 12.4 ランク

初期ランクは以下とし、DivisionはV2初期版では設けない。

- Bronze
- Silver
- Gold
- Platinum
- Diamond
- Master

### 12.5 PvP公平性

ランクPvPでは、ショップ由来の一時的な能力・疲労・練習効率ブーストをPvPスナップショットへ反映しない。

新入生候補追加・潜在能力鑑定など恒久的な育成判断へ影響するアイテムは通常ゲームへ反映するが、0円テスト期間は14.2の年度利用上限を全ユーザーへ同一条件で適用する。

直接「PvP勝利」「Rating増加」「能力+20」などを購入できるアイテムは禁止する。

## 13. PvP大会

V2初期実装では常設ランキングを優先する。

大会方式:

- 期間参加型
- 自動マッチ
- 非同期
- 勝敗履歴保存
- 最終順位報酬

リアルタイム同時接続は要求しない。

## 14. ショップ・テスト課金

### 14.1 テスト段階

課金アイテムUIは実装するが、すべて0円で購入可能にする。

実決済は接続しない。

購入可能数と使用可能数はサーバーで管理し、0円でも無制限連打はできない。

### 14.2 初期テストアイテムと年度上限

- 新入生候補追加: 1回/年度
- スカウト再調査: 2回/年度
- 潜在能力鑑定: 3回/年度
- 強化合宿: 1回/年度
- 疲労回復: 3回/年度
- 特別コーチ: 1回/年度
- 練習効率アップ: 1回/年度

年度切替時に各アイテムの年度利用回数をリセットする。

### 14.3 サーバー管理

所持数・使用履歴・購入履歴・年度利用回数はサーバー管理する。

同じリクエストの二重送信で重複付与されないよう、操作IDによる冪等性を持たせる。

## 17. UX状態管理

- success

### 17.2 二重操作防止

## 19. セーブ戦略

- 年度更新
- 新入生確定
- アイテム使用

- 保存中…
- 保存済み ✓
- オフライン保存

古いrevisionからの破壊的更新は拒否し、最新データ再読込を要求する。

## 20. セキュリティ・不正対策

- 認証必須
- PvP結果はサーバー計算またはサーバー再検証可能な入力のみ受理
- Rating更新はサーバーのみ
- アイテム付与はサーバーのみ
- 所持数変更はサーバーのみ
- APIにユーザーIDを任意指定させず、認証トークンから特定
- PvPスナップショットはバージョン管理
- 重要操作は操作IDを持たせ冪等にする

## 24. 完了条件

V2初期完成は以下をすべて満たした状態とする。

- アカウントなしでは本編へ入れない
- クラウドから同じ学校データを復元できる
- 3学年の世代交代を無期限に継続できる
- 学校評判に応じて新入生分布が変化する
- 稀に世界全体へ天才・怪物が出現する
- 選手タイプが能力値だけでなく成長・性格・特性でも異なる
- 県大会から全国大会まで年間進行できる
- 歴代学校・選手記録が蓄積する
- 他プレイヤーの保存チームと非同期対戦できる
- PvP Ratingとランキングが更新される
- テストショップのアイテムを0円で購入・使用できる
- 0円アイテムに年度利用上限が適用される
- ランクPvPでは一時的なショップブーストが除外される
- すべての主要通信操作で処理状態が視覚的に分かる
- 白画面・無反応・不明な長時間ローディングがない
- スマホとPCの主要E2Eが通る

## 25. 設計上の最終判断

Court Legacy V2は「キャラクターを集めるゲーム」ではなく、**学校そのものを何世代にもわたって育てるゲーム**とする。

選手は3年で卒業するからこそ価値があり、強い選手を永久保有させない。

プレイヤーの資産は特定選手ではなく、以下とする。

- 学校の歴史
- 評判
- 設備
- 監督実績
- 育成ノウハウ
- 歴代選手
- PvP実績

これにより、毎年の新入生への期待と、世代が変わっても続く長期プレイを両立する。
