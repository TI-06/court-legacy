# Court Legacy V2 Phase 8 — モバイルゲームループ再設計

## 1. 目的

Phase 8 では、既存の PvP・公式大会・ショップ・スカウト・チームダイナミクスを壊さずに、Court Legacy の日常プレイを「Web 管理画面」から「スマホ向け高校バレー育成ゲーム」へ再設計する。

今回の主目的は次の 6 点。

1. ユーザーに見える補助英語を原則廃止し、日本語 UI に統一する。
2. ホームをほぼ 1 画面に圧縮し、「今週何をするか」が即座に分かる構造へ変える。
3. 練習を即時実行型から「週間方針を設定し、週送り時に自動実行する」方式へ変更する。
4. 練習試合を無制限実行型ではなく、申込制・週 1 試合制・成長減衰付きへ変更する。
5. 疲労・コンディション・怪我から自動休養を判定し、プレイヤーが毎週細かく休養指定しなくても破綻しない育成ループを作る。
6. キャラクター画像を使わない前提で、選手・編成・大会表をスマホ 1 画面中心の高密度 UI に再構成する。

## 2. 今回の採用方針

### 2.1 練習試合

練習試合は「相手からの申込 + 自校からの申込」の両方を採用する。

- 他校から毎週一定確率で練習試合の申し込みが届く。
- 自校からも、その週に提示された候補校へ申し込める。
- 自校からの候補は原則 3 校程度とする。
- 1 週間に実施できる練習試合は原則 1 試合。
- 強豪校ほど成長効果が高いが、申し込み成功率は低い。
- 評判が高いほど、強い学校から申し込まれやすくなる。
- 同じ学校と短期間に繰り返し戦う場合は成長効果を減衰させる。

### 2.2 週進行

プレイヤー操作としては「次の週へ」を主要な確定アクションとする。

練習画面では練習内容を設定するだけで、その場では成長処理を行わない。

週送り時に、原則として次の順序で処理する。

1. 自動休養判定
2. 設定済みチーム練習
3. 個人重点育成
4. 練習成長・疲労・怪我判定
5. 予定済み練習試合
6. 練習試合による成長・信頼・士気・結束力変化
7. チームダイナミクス更新
8. イベント処理
9. 公式戦関連処理
10. 週末回復・怪我週数進行
11. 日付を 7 日進める
12. 次週の練習試合申込・候補生成
13. 週次レポート生成
14. ゲーム状態保存

この一連の処理は 1 回の週進行として確定し、途中状態をプレイヤーへ露出しない。

### 2.3 自動休養

自動休養は次の条件で判定する。

- 怪我中: 強制休養
- 疲労 65 以上: 自動休養
- コンディション 35 以下: 自動休養
- それ以外: 通常参加

自動休養対象者は原則として以下の扱いとする。

- チーム練習に参加しない。
- 個人重点育成に指定されていても、その週は実施しない。
- 練習試合には参加しない。
- 通常週末回復より疲労回復量を増やす。
- コンディション回復量を増やす。
- 休養自体から怪我悪化判定は発生させない。

公式戦は例外とする。

- 怪我中は出場不可。
- 疲労 65 以上・コンディション 35 以下は先発回避を優先するが、完全な出場禁止にはしない。
- 既存の安全交代・自動編成ロジックと整合させる。

## 3. データモデル

### 3.1 GameState schema

現行 `CURRENT_GAME_SCHEMA_VERSION = 4` から `5` へ上げる。

新たに GameState に永続化する週間管理状態を追加する。

概念モデル:

```ts
interface WeeklyScheduleState {
  trainingPlan: WeeklyPlan;
  practiceMatch: PracticeMatchScheduleState;
  recentPracticeOpponentIds: SchoolId[];
  latestReport: WeeklyReport | null;
}
```

実装時は責務を分け、必要であれば `weekly/` ドメイン配下に型を分離する。

### 3.2 練習設定

週間練習設定は UI のローカル state ではなくゲーム状態へ保存する。

保持対象:

- チーム練習メニュー
- 個人重点育成 2 枠
- 各重点育成の指示内容

原則として前週の設定を翌週へ引き継ぐ。

ただし次のケースでは安全に補正する。

- 卒業済み選手が個人枠に残っている。
- 対象選手が学校から離脱している。
- データ更新で指示 ID が存在しない。

この場合、週間進行自体を壊さず、有効な既定値へフォールバックする。

### 3.3 練習試合予定

練習試合状態には最低限、以下を持たせる。

```ts
type PracticeMatchScheduleState = {
  incomingOffer: PracticeMatchOffer | null;
  outgoingCandidates: PracticeMatchCandidate[];
  scheduledOpponentId: SchoolId | null;
  scheduledBy: "incoming" | "outgoing" | null;
};
```

候補・申込結果は同一週・同一 seed で再現可能にする。

ページ再読込や別クライアントからの再取得で候補が勝手に入れ替わってはならない。

### 3.4 練習試合履歴

無限育成対策用の履歴は永続化するが、無制限には保持しない。

用途:

- 同一校連戦の成長減衰
- 最近対戦した学校の候補頻度調整

保持期間または件数には上限を設ける。実装時の初期案は直近 8〜12 週間、または最大 12 件程度。

### 3.5 週次レポート

最新週の結果を UI で再表示できるよう、週次レポートを構造化して保持する。

最低限の内容:

- 対象週・日付
- 実施した練習
- 参加選手・休養選手
- 主要能力成長
- 疲労・コンディション変化
- 怪我発生・回復
- 練習試合結果
- 結束力・士気・評判変化
- 次週の練習試合申込
- 次の公式戦情報

全選手の詳細ログを永久保存する必要はなく、長期履歴は既存履歴へ必要な統計だけ反映する。

## 4. v4 → v5 移行

既存 v4 セーブは破棄しない。

移行時の初期値:

- `trainingPlan`: 現行データから有効な既定メニュー・選手を選択
- `incomingOffer`: null
- `outgoingCandidates`: 現在週の seed から生成
- `scheduledOpponentId`: null
- `recentPracticeOpponentIds`: []
- `latestReport`: null

v4 から v5 への移行は決定的で、同じ v4 セーブを複数回移行しても同一結果になること。

## 5. 週進行の原子性

現行の `training` / `practice-match` / `advance-week` の分離は、プレイヤー操作としては廃止する。

Phase 8 では、通常週のメインアクションを `advance-week` 系の単一コマンドへ集約する。

設計上の要件:

- 同じ revision に対する同じ operationId は二重適用しない。
- クラウドモードでは途中保存を公開しない。
- ローカルモードでも同じドメイン関数を使用する。
- 練習だけ実施済みで試合が未実施、という状態を作らない。
- 週進行失敗時は前 revision を保持する。
- 長期シミュレーションで決定性を維持する。

公式戦週は特別扱いとする。

公式戦が「今週」の場合、ホームの週送り導線から公式戦確認を挟む。公式戦結果を確定後、残りの週進行を同じ週次処理へ統合する。

## 6. 練習試合生成ルール

### 6.1 他校からの申込

申込発生率は学校評判に応じて上げる。

初期バランス案:

- 無名校: 15〜25%
- 地区有力校: 25〜35%
- 県内強豪: 40〜50%
- 全国級以上: 50〜65%

最終値はテストで調整する。

候補学校の強さ分布も評判に連動させる。

### 6.2 自校からの候補

毎週原則 3 校程度。

候補構成の目安:

1. 同格〜やや格下
2. 少し格上
3. チャレンジ枠

申し込み成功率は、主に次を入力とする。

- 自校評判
- 相手校評判
- 戦力差
- 最近の対戦頻度

リアル時間待ちは導入せず、申込時点で受諾・拒否を決定する。

## 7. 練習試合の成長設計

練習試合は育成手段として有効だが、最適解が「毎週同じ弱小校を殴る」にならないよう制御する。

### 7.1 相手強度補正

- 格上: 成長ボーナス
- 同格: 標準
- 格下: 成長減少

敗戦でも実戦経験による一定成長を認める。

### 7.2 同一校連戦減衰

初期案:

- 短期間 1 回目: 100%
- 2 回目: 70%
- 3 回目: 40%
- 4 回目以降: 20%

減衰判定は直近履歴だけで行い、古い対戦は徐々に影響から外す。

### 7.3 影響対象

参加選手へ以下を反映できる。

- 一部能力成長
- 士気
- 信頼
- キャリア出場記録
- チーム結束力

学校へ以下を反映できる。

- 評判ポイント
- 対戦履歴

数値は通常練習・公式戦・PvP のバランスを壊さない範囲に抑える。

## 8. PvP 境界

Phase 4 以降の ranked PvP の server-authoritative / frozen snapshot 方針を維持する。

次の情報は ranked PvP snapshot に含めない。

- 練習試合申込状態
- 次週候補
- 週次レポート
- 自動休養判定の一時情報
- 週間 UI 状態
- 未消化の週間成長補正

実際に確定済みの選手能力・状態など、通常の正規 GameState 結果のみが将来の公開 snapshot に反映される。

ショップ一時効果漏洩と同種の回帰を防ぐため、明示的なセキュリティ/境界テストを追加する。

## 9. ホーム画面

ホームは「今週の意思決定」に集中する。

390x844px 程度を基準に、主要操作をほぼ 1 画面へ収める。

必須表示:

- 学校名
- 日付・第何週
- 学校評判
- 今週の練習方針
- 個人重点育成の要約
- 自動休養人数
- 練習試合予定または申込通知
- 今週の公式戦
- チーム状態の短いサマリー
- 重要通知 1〜2 件
- 「次の週へ」固定アクション

ホームから削る/詳細へ移すもの:

- 長い現在状態レポート
- 詳細な直近試合内容
- 全選手の状態説明
- 重複するカード

詳細は各タブまたは BottomSheet へ移す。

## 10. 育成画面

育成画面の役割は「今週・今後の練習設定」。

廃止:

- 画面下の「練習を実行」

残す/追加:

- チーム練習メニュー変更
- 個人重点育成 2 枠
- 自動休養対象者のプレビュー
- 各メニューの成長・疲労・怪我リスク表示
- 「この設定は次週も引き継ぐ」の明示

自動休養判定は表示時点のプレビューであり、最終判定は週送り時の最新状態で行う。

## 11. 試合画面

試合タブは次の 3 系統を明確に分ける。

- 練習試合
- 公式戦
- 対人戦

### 11.1 練習試合

表示内容:

- 今週届いた申込
- 受ける / 断る
- 自校から申し込む候補
- 既に対戦予定がある場合は予定カード
- 相手戦力
- 成長期待
- 疲労負荷
- 申込成功率

練習試合はこの画面から即時実行しない。

### 11.2 公式戦

公式戦は重要イベントとして、今週の場合は確認を挟む。

### 11.3 対人戦

Phase 4 の ranked PvP フローは原則そのまま。

## 12. 練習試合結果と試合演出

週送り時に練習試合は自動計算するが、結果閲覧の自由度を残す。

週次レポートには最低限:

- 勝敗
- セットスコア
- 主な活躍選手
- 成長/結束/評判の主要変化

を表示する。

「試合詳細を見る」を押した場合のみ、既存 MatchScreen のダイジェスト表示を再利用する。

高速に進めたいユーザーは詳細を見ずに次週へ進められる。

## 13. 選手画面

キャラクター画像・生成ポートレート・独立パーツは使用しない。

選手詳細上部の大きなイニシャル/ヒーロー領域は縮小または廃止する。

390x844px で、原則スクロールなしに次を確認できることを目標とする。

- 名前
- 学年
- ポジション
- 身長
- 総合力
- 主要能力
- 疲労
- コンディション
- 士気
- 信頼
- チーム内役割

キャリア詳細・大会記録・細かい傾向は下部または詳細展開へ置く。

## 14. 編成画面

現行のコート直接編集は維持するが、上下の余白と英語補助見出しを削る。

画面表示は日本語統一。

例:

- MATCH ROSTER → チーム編成
- STARTING SIX → 先発6人
- DEFENSE SPECIALIST → リベロ
- SUBSTITUTES → ベンチ
- SAFETY POLICY → 交代設定

自動休養と安全編成の判定閾値が矛盾しないよう、Phase 8 実装時に既存 `resolveLockedStarters` の疲労閾値も整理する。

## 15. 大会表

現在の 700px 以上の固定横幅を前提としたブラケット UI は廃止する。

初期表示は「自校の勝ち上がり」を縦方向へ表示する。

表示切替:

- 自校ルート
- 全体表

全体表もラウンドごとの縦カードを基本とし、ページ全体の横スクロールを発生させない。

大会ロジック・16 校ブラケット自体は変更しない。

## 16. 日本語 UI ルール

ユーザー向け UI の装飾目的英語は原則使用しない。

対象例:

- YEAR
- NEXT ACTION
- WEEK PROGRESS
- PLAYER ROSTER
- MATCH ROSTER
- STARTING SIX
- SUBSTITUTES
- SAFETY POLICY
- PRACTICE MATCH
- LINEUP CHECK
- MATCH LIVE
- BRACKET
- CURRENT PLAN
- WEEKLY DEVELOPMENT
- HOME / AWAY

内部型・enum・変数名は英語のまま維持する。

ポジションも表示側は日本語化する。

- OH → アウトサイド
- MB → ミドルブロッカー
- OP → オポジット
- S → セッター
- L → リベロ

狭い一覧では必要に応じて短縮表記を併記してよいが、意味が日本語で理解できることを優先する。

## 17. モバイル UI 共通基準

対象 viewport:

- 320px
- 360px
- 390px
- 480px

基準:

- `document.body` / root で横スクロールを発生させない。
- 主要タップ領域は原則 44px 以上。
- 画像がない画面で巨大なヒーロー領域を作らない。
- 重要情報は常時表示、詳細情報は BottomSheet / 折りたたみ / 詳細画面へ退避。
- 見出し目的だけの英語小文字を並べない。
- 下部ナビゲーション `ホーム / 選手 / 育成 / 試合 / その他` は維持する。
- ホームの「次の週へ」は到達しやすい固定アクションとする。

## 18. エラー処理

週進行は状態更新の中心になるため、失敗時の挙動を明示する。

- 週進行が保存できない場合、次週画面へ遷移しない。
- revision conflict は最新 snapshot を再取得し、ユーザーに再実行を促す。
- ローカルモードでも例外発生時に壊れた snapshot を保存しない。
- 無効な週間練習設定は安全な既定値へ補正し、ゲーム起動不能にはしない。
- 練習試合候補生成に対象校が足りない場合は、候補数を減らして継続する。

## 19. テスト方針

### 19.1 ドメイン

必須境界テスト:

- 疲労 64 → 通常参加
- 疲労 65 → 自動休養
- コンディション 36 → 通常参加
- コンディション 35 → 自動休養
- 怪我中 → 強制休養
- 休養者の追加回復
- 休養者が練習成長を受けない
- 休養者が練習試合へ出場しない
- 1 週間 1 練習試合
- 格上成長補正
- 格下成長抑制
- 同校連戦減衰
- 同 seed / 同 state で同じ申込候補
- 評判差による候補品質変化
- 同一 operationId の二重週進行防止

### 19.2 移行

- v4 → v5 成功
- 既存選手・学校・大会・PvP・ショップ状態を保持
- 同じ v4 入力から同じ v5 を生成
- 無効な旧個人練習対象に安全フォールバック

### 19.3 PvP 境界

- 練習試合申込が PvP snapshot に入らない
- outgoingCandidates が入らない
- weekly report が入らない
- 一時的自動休養判定が入らない
- 確定済み能力値だけは通常どおり反映される

### 19.4 長期

- 30 年 equal-seed determinism
- 100 年 bounded soak
- 練習試合履歴が上限を超えて肥大化しない
- 週間レポートが無制限蓄積しない

### 19.5 モバイル E2E

320 / 360 / 390 / 480px で少なくとも次を確認する。

- ホーム
- 選手一覧
- 選手詳細
- 育成
- 編成
- 練習試合
- 大会表
- 週次レポート

全画面で body/document 横スクロールがないこと。

## 20. 実装アプローチ

採用: 既存 Phase 3〜7 を残し、週進行を新しい中心として UI を順に置換する。

実装順の推奨:

1. schema v5 と migration
2. weekly schedule domain
3. 自動休養
4. 週進行の一括 resolver
5. 練習試合申込・候補・成長制御
6. ローカル/API action wiring
7. ホーム再設計
8. 育成画面再設計
9. 試合タブ再設計
10. 週次レポート
11. 選手詳細圧縮
12. 編成画面日本語化・圧縮
13. 大会表再設計
14. 全画面日本語化監査
15. 長期/モバイル/PvP 回帰検証

## 21. 非目標

Phase 8 では以下を行わない。

- キャラクター画像・ポートレート生成の復活
- リアルマネー課金
- PvP Elo / season ルールの全面変更
- 公式大会フォーマットの全面変更
- 新スポーツ追加
- リアルタイム対人戦
- 練習試合申込をリアル時間待ちにすること

## 22. 成功条件

Phase 8 完了時、プレイヤーは次の感覚で遊べること。

1. アプリを開く。
2. ホーム 1 画面で今週の状況を把握する。
3. 必要なら練習・編成・練習試合予定だけ調整する。
4. 「次の週へ」を押す。
