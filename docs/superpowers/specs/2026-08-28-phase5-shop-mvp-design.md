# Court Legacy V2 Phase 5 — Shop MVP Design

## 1. Purpose

Phase 5 adds the first server-authoritative shop and item system to Court Legacy V2.

The goal is not to add real payment processing. The goal is to create a production-shaped shop foundation that can later support real payment without changing the game-authority boundary.

For the Phase 5 test period:

- every item costs `¥0`;
- no payment provider or checkout SDK is connected;
- purchase, inventory, use history, annual limits, and item effects are authoritative on the Worker/Supabase side;
- zero-price items still have strict annual purchase/use limits;
- items bought in one in-game academic year do not carry into the next year;
- item effects must not provide a direct PvP win/rating purchase path;
- every asynchronous action has a visible pending/success/error state.

Phase 5 deliberately excludes school historical records, Hall of Fame, asynchronous PvP tournaments, and real-money checkout.

---

## 2. Product principles

### 2.1 Items add decisions, information, or training opportunities

The shop must not become a direct power sale.

Allowed effects:

- add one more scouting candidate generated by normal recruitment rules;
- improve the precision of scouting information;
- reveal a narrow potential estimate without exposing the exact hidden potential value;
- create an additional training opportunity that still obeys normal player growth constraints;
- reduce fatigue/raise condition within bounded values;
- provide one targeted coaching opportunity;
- boost the next normal weekly training growth calculation.

Forbidden effects:

- buy a PvP victory;
- add PvP rating directly;
- set player ability to an arbitrary client-supplied value;
- bypass potential/growth-type constraints with a fixed large stat injection;
- expose hidden player truth fields directly to the browser.

### 2.2 Server authority

The browser may request an item operation but may not decide:

- price;
- annual limit;
- owned quantity;
- effect strength;
- target eligibility;
- hidden scouting truth;
- resulting player stats;
- resulting scouting candidate truth.

Those values are resolved by trusted server code and committed by database RPCs.

### 2.3 No opaque waiting

The shop follows the V2 UX rule that users must always be able to see whether work is still in progress.

Examples:

- `ショップ情報を読み込んでいます…`
- `購入処理中…`
- `購入しました ✓`
- `使用準備中…`
- `効果を反映中…`
- `保存中…`
- `完了しました ✓`
- `購入結果を確認できませんでした [状態を確認]`
- `ゲームデータが更新されています [最新状態を読み込む]`

A shop operation must never replace the entire app with a blank screen.

## 3. Scope

Phase 5 contains:

1. seven fixed test item definitions;
2. shop catalog API;
3. current-year inventory API;
4. zero-price purchase API;
5. item-use API;
6. annual purchase/use limits;
7. current-year item expiration;
8. operation-id idempotency;
9. game-save revision conflict handling;
10. atomic inventory/game/scouting mutations;
11. persistent scouting insight upgrades;
12. shop UI and inventory UI;
13. direct use actions from scouting cards where appropriate;
14. visible operation progress and retry states;
15. mobile E2E coverage;
16. PvP leakage regression tests.

Phase 5 does not contain:

- Stripe or any other payment processor;
- premium currency;
- consumables with cross-year stockpiling;
- direct PvP consumables;
- item gifting/trading;
- loot boxes;
- limited-time external campaigns;
- subscriptions.

## 5. Item effects

### 5.1 `extra-scout-candidate`

Effect:

- append exactly one candidate to the current scouting candidate pool;
- generate the candidate with the existing recruitment probability model for the current school/year;
- school reputation, school facilities, region, existing V2 generation rules, and deterministic server random state still apply;
- the item must not guarantee `elite`, `generational`, `monster`, or any other tier;
- candidate hidden truth remains Worker/database-only.

The operation mutates the candidate pool atomically with inventory/use-history/revision changes.

### 5.2 `scout-research`

Effect:

- target one current-cycle candidate;
- do not regenerate or alter the candidate truth;
- persist an insight upgrade for the targeted candidate;
- subsequent scouting-board reads generate a narrower overall/potential estimate and `high` confidence;
- exact hidden ability, tier, hidden traits, growth peak, injury resistance, and exact potential remain hidden.

Persistent insight level:

- `overallPrecision = researched`;
- `potentialPrecision = researched` unless already `appraised`.

For `researched` reports, the server uses scouting information quality equivalent to at least `90` while still returning ranges, not truth values.

### 5.3 `potential-appraisal`

Effect:

- target one current-cycle candidate;
- do not alter candidate truth;
- persist `potentialPrecision = appraised`;
- subsequent reports keep the exact potential hidden;
- the public `estimatedPotential` range is constrained to a maximum half-width of `2` around a server-generated estimate, clamped to 0–100;
- overall ability precision is unchanged unless the candidate was separately researched.

This means an actual potential of 82 may be shown around `80–84`; it is never returned as a dedicated exact `potential: 82` field.

### 5.4 `training-camp`

Effect:

- execute an immediate team-wide special training resolution;
- injured players are skipped;
- growth uses the existing `calculateGrowth()` rules for grade, growth type, personality, facilities, coach, fatigue, condition, and academics;
- the special camp uses a dedicated server-side activity definition rather than accepting any growth numbers from the browser;
- target abilities are selected from a balanced camp profile so all active players have a meaningful but bounded chance to grow;
- base growth is intentionally below the sum of a normal weekly team menu plus two individual assignments, so the camp is valuable but not equivalent to buying an extra full week;
- camp fatigue is positive and processed through the existing conditioning/recovery-room fatigue rules;
- existing injury-risk logic applies;
- the result response includes public summary data such as participating players, players who grew, total ability growth, top growth logs, and average fatigue change.

Implementation should reuse/extract existing training primitives instead of maintaining a second independent growth formula.

### 5.5 `fatigue-recovery`

Target: one current-school player.

Effect:

- `fatigue = max(0, fatigue - 40)`;
- `condition = min(100, condition + 10)`;
- injury is unchanged;
- ability, potential, morale, trust, and hidden traits are unchanged;
- a player whose fatigue is already 0 and condition is already 100 is not an eligible target, preventing a no-op item use.

The result returns public before/after fatigue and condition values.

### 5.6 `special-coach`

Target: one non-injured current-school player plus one allowed focus.

Allowed focus values:

- `spike`;
- `serve`;
- `receive`;
- `block`;
- `physical`;
- `decision`.

Mapping:

- `spike` → spike/jump;
- `serve` → serve/mental;
- `receive` → receive/speed;
- `block` → block/jump;
- `physical` → stamina/speed/jump;
- `decision` → decision/set/mental.

Effect:

- execute one dedicated individual training activity through the same growth/fatigue/injury primitives used by normal training;
- server code owns target-ability mapping, base growth, fatigue, and injury risk;
- normal potential/growth-type/facility/coach/fatigue/condition/academic rules still apply;
- it does not directly assign a fixed ability bonus.

The result returns public ability changes, fatigue change, condition change, and injury result.

### 5.7 `training-efficiency-boost`

Effect on use:

- consume the inventory item;
- set a pending game effect representing `+20%` growth on the next successfully resolved normal weekly training action;
- using another copy while the effect is already pending is not allowed;
- the pending effect is not consumed by viewing the training screen, submitting an invalid plan, or a revision-conflicted request;
- it is consumed only inside the same successful transaction that commits a valid normal weekly training result.

Training calculation:

- the existing growth result receives a named `shop-training-boost` modifier of `120%`;
- the boost applies to growth, not fatigue/injury/academic participation rules;
- it must be visible in the returned training modifier/result UI;
- after that training commits, the pending effect disappears.

## 6. GameState change

Inventory does not belong in the main `GameState` JSON.

The only shop-related state stored in `GameState` is a gameplay effect that must participate in the next authoritative game action.

Add an optional structure equivalent to:

```ts
interface ShopGameEffects {
  nextTrainingGrowthBoost?: {
    percent: 20;
    remainingUses: 1;
    sourceItemId: "training-efficiency-boost";
  };
}
```

`GameState` gains `shopEffects?: ShopGameEffects` and the game-state schema/codec is updated in the normal V2 migration-compatible manner.

The PvP snapshot builder must not serialize this field or any equivalent transient shop metadata.

## 7. Persistence model

### 7.1 `shop_item_definitions`

Server-owned catalog rows.

Minimum columns:

- `item_id` primary key;
- `display_name`;
- `description`;
- `price_yen`;
- `annual_purchase_limit`;
- `annual_use_limit`;
- `effect_type`;
- `enabled`;
- `sort_order`;
- timestamps.

The seven Phase 5 rows are inserted by migration/seed SQL. Browser roles may not mutate this table.

### 7.2 `shop_inventory`

Current and historical item grants.

Minimum columns:

- `inventory_id`;
- `user_id`;
- `item_id`;
- `academic_year_index`;
- `quantity_remaining`;
- timestamps.

Active inventory is defined by `academic_year_index = current GameState.yearIndex` and `quantity_remaining > 0`.

Old rows remain historical/auditable but are not usable in later academic years.

### 7.3 `shop_transactions`

Purchase audit/idempotency history.

Minimum columns:

- `transaction_id`;
- `user_id`;
- `operation_id`;
- `item_id`;
- `academic_year_index`;
- `price_yen`;
- `result` JSON;
- timestamp.

Unique constraint:

- `(user_id, operation_id)`.

### 7.4 `shop_item_uses`

Use audit/idempotency history.

Minimum columns:

- `use_id`;
- `user_id`;
- `operation_id`;
- `item_id`;
- `academic_year_index`;
- `target_type`;
- `target_id` nullable;
- `request_payload` safe subset;
- `result` public-safe JSON;
- timestamp.

Unique constraint:

- `(user_id, operation_id)`.

### 7.5 `shop_yearly_counters`

Minimum columns:

- `user_id`;
- `item_id`;
- `academic_year_index`;
- `purchased_count`;
- `used_count`;
- updated timestamp.

Primary/unique key:

- `(user_id, item_id, academic_year_index)`.

Rows are not deleted on year transition. A new academic year naturally starts from no row/zero counters.

### 7.6 `scouting_candidate_insights`

Persists item-created information improvements without modifying candidate truth.

Minimum columns:

- `user_id`;
- `cycle_key`;
- `candidate_id`;
- `overall_precision` enum-like value: `normal | researched`;
- `potential_precision` enum-like value: `normal | researched | appraised`;
- timestamps.

Unique key:

- `(user_id, cycle_key, candidate_id)`.

This table contains no copy of exact candidate abilities/potential.

## 8. Security and RLS boundary

Raw shop/inventory/history tables and scouting insight persistence are server-managed.

Requirements:

- enable RLS on Phase 5 tables;
- revoke direct browser-role writes (`anon`, `authenticated`) to authoritative shop mutations;
- mutation RPC execution is limited to trusted service role/Worker usage;
- the browser uses the Cloudflare Worker API only;
- browser public DTOs do not include candidate `Player`, exact `potential`, `tier`, hidden trait ids, growth peak, injury resistance, exact scouting truth, or server-only effect definitions.

Source-boundary regression tests should prevent frontend imports from Worker data stores/server-only item-effect modules.

## 9. API contracts

### 9.1 Catalog/status

`GET /api/shop`

Returns one browser-safe combined response so the screen does not need multiple independent blocking fetches.

Each item includes:

- `itemId`;
- `displayName`;
- `description`;
- `priceYen` (`0` in Phase 5);
- `annualPurchaseLimit`;
- `annualUseLimit`;
- `purchasedThisYear`;
- `usedThisYear`;
- `quantityOwnedThisYear`;
- `canPurchase`;
- `purchaseBlockedReason` nullable;
- `canUse`;
- `useBlockedReason` nullable.

No hidden effect parameters are required by the browser.

### 9.2 Purchase

`POST /api/shop/purchase`

Browser request:

```ts
{
  operationId: string;
  revision: number;
  itemId: string;
}
```

The browser does not send quantity, price, annual limits, or effect values.

Success returns:

- replay-safe `operationId`;
- updated game revision/snapshot metadata required by the app;
- updated public shop status for the purchased item;
- a public success outcome.

### 9.3 Use

`POST /api/shop/use`

Browser request uses a discriminated public target shape:

```ts
{
  operationId: string;
  revision: number;
  itemId: string;
  target?:
    | { type: "player"; playerId: string }
    | { type: "scouting-candidate"; candidateId: string }
    | { type: "special-coach"; playerId: string; focus: SpecialCoachFocus };
}
```

The Worker rejects a target shape that is not valid for the item definition.

Success returns:

- updated game snapshot/revision where applicable;
- updated public shop status;
- a browser-safe item-specific result DTO;
- updated scouting report(s) when a scouting insight operation changes the visible board.

### 9.4 Error semantics

Use stable machine-readable codes with Japanese user-facing messages.

Required categories:

- `revision_conflict` → HTTP 409;
- `operation_replay` is not an error: return the stored successful result;
- `item_not_found`;
- `item_disabled`;
- `purchase_limit_reached`;
- `use_limit_reached`;
- `inventory_empty`;
- `inventory_expired`;
- `invalid_target`;
- `target_not_found`;
- `effect_already_pending`;
- `scouting_cycle_unavailable`;
- `server_error`.

A network timeout/unknown client state must be recoverable by retrying the same `operationId` or explicitly reloading shop status.

## 10. Purchase transaction

The purchase RPC must lock/validate enough state to make the following one atomic operation:

1. replay an existing `(user_id, operation_id)` result if present;
2. lock/read current game save;
3. verify expected revision;
4. derive current `yearIndex` from authoritative stored `GameState`;
5. load authoritative item definition;
6. verify item enabled and price `0` for Phase 5;
7. lock/create the current annual counter;
8. enforce annual purchase limit;
9. increment current-year inventory quantity;
10. increment `purchased_count`;
11. write transaction history/result;
12. increment game save revision so stale clients cannot subsequently mutate from the old revision;
13. return the committed result.

A duplicate request cannot grant a second item.

---

## 11. Use transaction

Each item use must be atomic across every authoritative resource it changes.

Common sequence:

1. replay existing operation result if present;
2. lock/read game save;
3. verify revision;
4. derive current `yearIndex`;
5. lock item definition, current-year inventory, and annual counter;
6. verify quantity and annual use limit;
7. validate the target against authoritative game/scouting data;
8. calculate the effect in trusted code;
9. mutate GameState and/or scouting persistence as required;
10. decrement inventory;
11. increment annual `used_count`;
12. write public-safe use history/result;
13. increment game revision;
14. return committed result.

If any step fails, none of inventory, GameState, scouting data, counters, or history is partially committed.

For `extra-scout-candidate`, the RPC/transaction must include candidate-pool mutation.

For `scout-research` and `potential-appraisal`, the RPC/transaction must include candidate-insight upsert.

For training/recovery effects, the transaction must include the new GameState.

---

## 12. Academic-year behavior

Shop year means the game's academic year, not the real-world calendar year.

Authoritative key:

- `GameState.yearIndex`.

Behavior on year transition:

- old annual counter rows remain untouched;
- old inventory remains in history but is inactive because its `academic_year_index` no longer matches the current game year;
- new-year catalog status starts with `purchasedThisYear = 0`, `usedThisYear = 0`, and `quantityOwnedThisYear = 0` until new operations occur;
- no cron job or destructive reset is required.

This keeps long-running saves deterministic and avoids reset-time failure modes.

A pending `training-efficiency-boost` is a GameState gameplay effect. If the academic year transitions before it is consumed, it expires during the transition and is not carried into the new year.

---

## 13. Scouting integration

The current scouting candidate truth store remains the source of truth.

Public scouting-board generation becomes:

1. load current-cycle candidate truth on the Worker;
2. load per-candidate insight levels;
3. generate browser-safe ScoutReports using the appropriate precision policy;
4. return only the public report.

The browser never receives the underlying `Player` candidate objects.

Direct actions on scouting cards:

- `スカウト再調査` when inventory/status allows;
- `潜在能力鑑定` when inventory/status allows.

These buttons consume existing inventory; purchasing remains in the Shop screen.

---

## 14. Normal-training integration

`training-efficiency-boost` must integrate with the authoritative normal training action rather than creating a parallel client path.

When applying a valid normal training action:

1. detect the pending boost in authoritative GameState;
2. pass an explicit growth multiplier/modifier into extracted/reused training primitives;
3. resolve the training normally;
4. include `shop-training-boost` in public growth modifiers/logs;
5. clear the pending boost in the resulting GameState;
6. commit training and effect consumption together through the existing game-operation atomic save path.

If training validation fails or persistence conflicts, the boost remains pending.

---

## 15. PvP boundary

PvP must never copy transient shop metadata into a published snapshot.

Explicitly excluded from public/PvP snapshot contracts:

- inventory;
- purchase/use history;
- annual shop counters;
- `shopEffects` / pending training boost;
- scouting insights;
- shop effect definitions.

Permanent ability changes legitimately earned through a successfully committed training camp, special coach session, or boosted normal training remain part of the player's resulting base GameState and therefore may affect later PvP snapshots. The temporary buff itself does not.

Regression tests must inspect both source boundaries and serialized snapshot/public DTOs.

## 16. UI information architecture

The existing five-tab bottom navigation does not change.

Path:

- `その他` → `ショップ`.

The Shop screen contains two local views:

- `商品`;
- `所持品`.

### 16.1 Product card

Each product card shows:

- item name;
- short effect description;
- annual use status, e.g. `年度利用 1 / 3`;
- current-year owned quantity;
- `¥0`;
- purchase button or blocked reason.

The UI prioritizes effect/limits over price decoration.

### 16.2 Inventory

Inventory lists only current-year items with quantity > 0.

Each row shows:

- name;
- quantity;
- `今年度のみ有効`;
- use action when usable;
- explanation when use requires a different context (for example scouting-card target selection).

### 16.3 Target selection

Player-target items:

- fatigue recovery sorts eligible players by fatigue descending;
- special coach shows eligible non-injured players and then focus selection.

Scouting-target items:

- use directly from ScoutingScreen candidate cards.

Targetless items:

- extra scouting candidate;
- training camp;
- training efficiency boost;

use a confirmation panel/dialog with effect summary.

### 16.4 Result display

Do not show only `アイテムを使用しました`.

Examples:

- fatigue recovery: fatigue/condition before → after;
- scouting research: old estimate/confidence → new estimate/confidence;
- potential appraisal: old potential range → new narrow range;
- training camp: participants, players who grew, total growth, top growth, average fatigue change;
- special coach: changed abilities, fatigue/condition, injury outcome;
- training efficiency boost: persistent badge `次回練習 成長効率 +20%` until consumed.

## 17. Loading, retry, and unknown-result UX

### Catalog load

- local shop loading skeleton/status;
- existing app navigation/header remains visible;
- retry button on failure.

### Purchase/use pending

Only the active operation is disabled. The whole application is not frozen.

### Network failure after submission

The UI must distinguish an unknown result from a confirmed rejection.

Message example:

`購入結果を確認できませんでした。状態を確認できます。`

The app may retry the same `operationId`; idempotency determines whether to execute or replay.

### Revision conflict

Show:

`ゲームデータが別の操作で更新されています。最新状態を読み込んでください。`

Provide a clear reload action. Do not silently overwrite newer state.

## 19. Testing strategy

### 19.1 Domain tests

Cover:

- catalog definition invariants;
- annual limit evaluation;
- current-year inventory eligibility;
- fatigue recovery clamping/no-op validation;
- special coach focus mapping;
- training camp bounded growth/fatigue/injury behavior;
- training boost modifier and one-use consumption;
- scouting precision policies never expose exact hidden fields;
- deterministic item effect resolution from identical authoritative input/seed.

### 19.2 Store/RPC tests

Cover:

- first purchase;
- duplicate purchase operation replay;
- purchase limit rejection;
- first use;
- duplicate use operation replay;
- use limit rejection;
- empty/expired inventory rejection;
- revision conflict leaves inventory/game unchanged;
- atomic rollback on simulated failure;
- scouting-pool/insight mutation atomicity;
- concurrent requests cannot exceed annual limits.

### 19.3 UI tests

Cover:

- product/inventory states;
- visible loading/success/error states;
- blocked annual limit messaging;
- fatigue target ordering;
- scouting direct-use actions;
- before/after result presentation;
- training-boost pending badge.

### 19.4 E2E

Required mobile scenarios:

1. `その他 → ショップ → 疲労回復を¥0購入 → 購入処理中表示 → 所持数+1`;
2. `所持品 → 疲労回復 → 選手選択 → 効果反映中表示 → fatigue減少 → 所持数-1`;
3. same purchase `operationId` twice grants once;
4. annual limit reached blocks the next use without state mutation;
5. stale revision returns conflict and does not consume inventory;
6. year transition invalidates prior-year inventory and exposes fresh limits;
7. scouting research/appraisal changes public report precision without hidden truth leakage;
8. training boost is visibly pending, applies to one valid training, then disappears;
9. PvP publish/result DTOs contain no transient shop metadata;
10. existing PvP and scouting E2E remain green.

## 20. Completion criteria

Phase 5 is complete only when all of the following are true:

- all seven items appear in the catalog;
- all Phase 5 prices are `¥0`;
- no real-payment code is present;
- purchase and use are server authoritative;
- annual purchase/use limits are server enforced;
- old-year inventory is unusable without a destructive reset job;
- purchase/use operations are idempotent;
- revision conflicts are safe and visible;
- inventory + GameState + counters + history update atomically;
- scouting item operations preserve hidden-truth boundaries;
- normal training boost consumes exactly once on successful training;
- transient shop metadata does not enter PvP snapshots/public PvP DTOs;
- loading/success/error/unknown-result states are visible;
- 320/360/390/480px layout audit remains green;
- required unit/integration/E2E tests pass;
- `npm run verify` passes;
- `npm run test:e2e` passes;
- final diff review finds no browser direct-write path to authoritative shop tables and no duplicate item-effect write path.

The implementation PR remains Draft/unmerged until the stacked prerequisite Phase 3/Phase 4 integration state is resolved and merge is explicitly authorized.
