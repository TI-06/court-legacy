# Court Legacy V2 Phase 5 — Shop MVP Design

## 1. Purpose

Phase 5 adds the first server-authoritative shop and item system to Court Legacy V2.

The goal is not real payment. The goal is a production-shaped foundation that can later support real payment without changing the game-authority boundary.

For the Phase 5 test period:

- every item costs `¥0`;
- no payment provider or checkout SDK is connected;
- purchase, inventory, use history, annual limits, and effects are authoritative on Worker/Supabase;
- zero-price items still have strict annual purchase/use limits;
- current-year free inventory never carries into the next in-game academic year;
- items may improve information or create bounded training opportunities, but cannot directly buy PvP wins/rating;
- every asynchronous action has a visible pending/success/error/unknown-result state.

Phase 5 excludes school historical records, Hall of Fame, PvP tournaments, real-money checkout, premium currency, gifting/trading, loot boxes, subscriptions, and externally scheduled campaigns.

---

## 2. Product principles

### 2.1 What items are allowed to do

Allowed:

- add one scouting candidate generated by the normal recruitment model;
- improve scouting-report precision without exposing hidden truth;
- create bounded extra training opportunities using existing growth rules;
- reduce fatigue and improve condition within fixed limits;
- boost the next normal weekly training calculation once.

Forbidden:

- direct PvP victory or rating grants;
- arbitrary client-supplied stat changes;
- fixed large stat injections that bypass growth constraints;
- exact hidden `potential`, `tier`, hidden traits, growth peak, injury resistance, or candidate `Player` objects in browser DTOs.

### 2.2 Server authority

The browser may request an operation but does not decide price, quantity, annual limits, effect strength, target eligibility, hidden scouting truth, resulting stats, or random outcomes.

### 2.3 No opaque waiting

Examples of required visible states:

- `ショップ情報を読み込んでいます…`
- `購入処理中…`
- `購入しました ✓`
- `使用準備中…`
- `効果を反映中…`
- `保存中…`
- `完了しました ✓`
- `購入結果を確認できませんでした [状態を確認]`
- `ゲームデータが更新されています [最新状態を読み込む]`

Shop work must never blank or globally freeze the app.

## 5. Exact item behavior

### 5.1 `extra-scout-candidate`

- usable only while the current scouting cycle exists;
- append exactly one new current-cycle candidate;
- existing six candidates must not be rerolled or replaced;
- generation uses the same school reputation, coach scouting, scouting-network, dormitory, recent-season rating, name exclusion, tier probabilities, and deterministic server RNG rules as the existing pool;
- implementation should extract a deterministic candidate-at-index primitive from the current six-candidate generator and create index `7` for this Phase 5 item;
- hidden candidate truth stays server-only;
- no tier is guaranteed.

### 5.2 `scout-research`

- target one current-cycle candidate;
- candidate truth never changes;
- persist `overallPrecision = researched`;
- persist `potentialPrecision = researched` unless already `appraised`;
- researched report generation uses effective information quality `max(normalQuality, 90)`;
- confidence is `high`;
- report remains range-based;
- report seed includes cycle/candidate/precision state, so refreshes are stable and cannot reroll estimates.

### 5.3 `potential-appraisal`

- target one current-cycle candidate;
- candidate truth never changes;
- persist `potentialPrecision = appraised`;
- exact potential is never returned;
- public `estimatedPotential` has maximum half-width `2`, clamped 0–100;
- overall precision is unchanged unless separately researched;
- report seed includes the persisted precision state, so refreshes remain stable.

### 5.4 `training-camp`

Execute immediate team-wide special training using extracted/reused normal training primitives.

Per non-injured player, use a deterministic preferred-position profile:

- OH → `spike`, `receive`, `serve`;
- MB → `block`, `jump`, `speed`;
- OP → `spike`, `serve`, `block`;
- S → `set`, `decision`, `speed`;
- L → `receive`, `speed`, `mental`.

Fixed server activity values:

- `baseGrowth = 3`;
- `fatigue = 12`;
- `injuryRisk = 5`;
- `trustGrowth = 2`.

Growth still uses current grade, growth type, personality, facilities, coach, fatigue, condition, and academic restrictions. Fatigue/injury still use existing conditioning/recovery/injury logic. Injured players are skipped. The browser cannot override these constants.

Public result includes participant count, grew-player count, total ability growth, top growth logs, average fatigue change, and injuries.

### 5.5 `fatigue-recovery`

Target one current-school player.

- `fatigue = max(0, fatigue - 40)`;
- `condition = min(100, condition + 10)`;
- injury, ability, potential, morale, trust, and hidden traits do not change;
- a player with `fatigue = 0` and `condition = 100` is ineligible, preventing no-op consumption.

Return before/after fatigue and condition.

### 5.6 `special-coach`

Target one non-injured current-school player plus one focus.

Allowed focus mapping:

- `spike` → `spike`, `jump`;
- `serve` → `serve`, `mental`;
- `receive` → `receive`, `speed`;
- `block` → `block`, `jump`;
- `physical` → `stamina`, `speed`, `jump`;
- `decision` → `decision`, `set`, `mental`.

Fixed server activity values:

- `baseGrowth = 8`;
- `fatigue = 6`;
- `injuryRisk = 4`;
- `trustGrowth = 3`.

It uses the same growth/fatigue/injury primitives as normal training and therefore still obeys player/school constraints. It never writes a fixed ability bonus directly.

### 5.7 `training-efficiency-boost`

On use:

- consume one inventory item;
- set a pending gameplay effect for the next successfully committed normal weekly training;
- pending value is exactly `+20%` growth;
- a second copy cannot be activated while one is pending;
- invalid training, network failure before commit, or revision conflict does not consume the pending effect.

On normal training:

- add a named `shop-training-boost` growth modifier of `120%` before final growth rounding/flooring;
- do not modify fatigue, injury risk, or academic participation rules;
- consume the pending effect in the same successful game-operation commit as the training result.

## 6. GameState boundary

Inventory is not stored in `GameState`.

Only gameplay state required by a later authoritative action is stored there:

```ts
interface ShopGameEffects {
  nextTrainingGrowthBoost?: {
    percent: 20;
    remainingUses: 1;
    sourceItemId: "training-efficiency-boost";
  };
}
```

`GameState` gains optional `shopEffects`. The state schema/codec is upgraded through the normal V2 compatibility path.

If an academic-year transition occurs before the pending training boost is consumed, the transition removes it.

PvP snapshot/public contracts never serialize `shopEffects`.

## 7. Persistence

### 7.1 `shop_item_definitions`

Server-owned catalog:

- `item_id` PK;
- `display_name`;
- `description`;
- `price_yen`;
- `annual_purchase_limit`;
- `annual_use_limit`;
- `effect_type`;
- `enabled`;
- `sort_order`;
- timestamps.

### 7.2 `shop_inventory`

- `inventory_id`;
- `user_id`;
- `item_id`;
- `academic_year_index`;
- `quantity_remaining`;
- timestamps.

Active inventory means `academic_year_index = authoritative GameState.yearIndex` and `quantity_remaining > 0`.

### 7.3 `shop_operations` — canonical idempotency ledger

This is the only idempotency authority for Phase 5 shop mutations.

- `operation_id`;
- `user_id`;
- `operation_type` = `purchase | use`;
- `request_fingerprint`;
- `response` public-safe JSON;
- timestamp.

Unique key:

- `(user_id, operation_id)`.

If the same operation ID is replayed with the same fingerprint/type, return the stored response. If reused with different semantics, reject with `operation_id_reused` and mutate nothing.

This prevents a purchase and a use from independently accepting the same operation ID.

### 7.4 `shop_transactions`

Purchase audit rows reference the canonical operation:

- `transaction_id`;
- `user_id`;
- `operation_id` FK/logical reference;
- `item_id`;
- `academic_year_index`;
- `price_yen`;
- timestamp.

### 7.5 `shop_item_uses`

Use audit rows:

- `use_id`;
- `user_id`;
- `operation_id`;
- `item_id`;
- `academic_year_index`;
- `target_type`;
- `target_id` nullable;
- safe request subset;
- public-safe result JSON;
- timestamp.

### 7.6 `shop_yearly_counters`

- `user_id`;
- `item_id`;
- `academic_year_index`;
- `purchased_count`;
- `used_count`;
- updated timestamp.

Unique key `(user_id, item_id, academic_year_index)`.

Rows are append-by-year and are never destructively reset.

### 7.7 `scouting_candidate_insights`

- `user_id`;
- `cycle_key`;
- `candidate_id`;
- `overall_precision`: `normal | researched`;
- `potential_precision`: `normal | researched | appraised`;
- timestamps.

Unique key `(user_id, cycle_key, candidate_id)`.

No exact candidate truth is duplicated here.

## 8. Security/RLS

- enable RLS on all new authoritative tables;
- revoke browser-role mutation access (`anon`, `authenticated`);
- mutation RPCs are service-role/Worker only;
- frontend uses Worker APIs only;
- frontend source-boundary tests forbid imports from Worker ShopStore/SupabaseShopStore/server effect modules;
- public DTO tests forbid candidate `Player`, exact potential/tier/hidden traits/growth peak/injury resistance, inventory internals, operation ledger internals, and transient shop effect metadata in PvP.

## 9. Browser API

### 9.1 `GET /api/shop`

Return one browser-safe catalog/status response containing per item:

- `itemId`, `displayName`, `description`, `priceYen`;
- annual purchase/use limits;
- purchased/used this year;
- quantity owned this year;
- `canPurchase` + blocked reason;
- `canUse` + blocked reason.

No hidden effect constants are required by the browser.

### 9.2 `POST /api/shop/purchase`

Request:

```ts
{ operationId: string; revision: number; itemId: string }
```

Browser does not send quantity, price, limits, or effect values.

### 9.3 `POST /api/shop/use`

Request:

```ts
{
  operationId: string;
  revision: number;
  itemId: string;
  target?:
    | { type: "player"; playerId: string }
    | { type: "scouting-candidate"; candidateId: string }
    | { type: "special-coach"; playerId: string; focus: SpecialCoachFocus };
}
```

Worker validates that target shape matches the authoritative item definition.

### 9.4 Errors

Stable codes include:

- `revision_conflict` (409);
- `operation_id_reused`;
- `item_not_found`;
- `item_disabled`;
- `purchase_limit_reached`;
- `use_limit_reached`;
- `inventory_empty`;
- `inventory_expired`;
- `invalid_target`;
- `target_not_found`;
- `effect_already_pending`;
- `scouting_cycle_unavailable`;
- `server_error`.

A confirmed replay is success, not an error.

## 10. Purchase atomic transaction

One DB RPC performs:

1. check `shop_operations` for replay/reuse;
2. lock/read current game save;
3. verify expected revision;
4. derive authoritative `yearIndex`;
5. load item definition;
6. verify enabled and Phase 5 price `0`;
7. lock/create yearly counter;
8. enforce purchase limit;
9. increment current-year inventory;
10. increment `purchased_count`;
11. write purchase audit;
12. write canonical operation response;
13. increment game-save revision even though GameState content is unchanged, so stale clients cannot race a later mutation;
14. return committed public result.

Either all commit or none commit.

---

## 11. Use atomic transaction

Common path:

1. check canonical operation replay/reuse;
2. lock/read game save;
3. verify revision;
4. derive current `yearIndex`;
5. lock item definition, current-year inventory, yearly counter;
6. enforce quantity/use limit;
7. validate target against authoritative game/scouting data;
8. resolve effect in trusted code;
9. mutate GameState and/or scouting persistence;
10. decrement inventory;
11. increment `used_count`;
12. write use audit;
13. write canonical operation response;
14. increment revision;
15. return result.

`extra-scout-candidate` includes candidate-pool mutation in the same SQL transaction. `scout-research`/`potential-appraisal` include insight upsert in the same transaction. Training/recovery items include the updated GameState in the same transaction.

A failure leaves inventory, GameState, scouting data, counters, and histories unchanged.

---

## 12. Academic-year behavior

The shop year is the in-game `GameState.yearIndex`, never the real calendar year.

On year transition:

- old counters remain as history;
- old inventory remains stored but inactive;
- new year has zero counters/active inventory until new operations;
- no cron/reset delete job exists;
- pending training boost expires during the transition.

---

## 13. Scouting integration

Current candidate truth store remains authoritative.

Board generation becomes:

1. load current-cycle candidate truth;
2. load candidate insight levels;
3. build browser-safe reports using precision policy;
4. seed each report deterministically from state seed + cycle + candidate ID + precision state;
5. return only public reports.

Refreshing cannot reroll a better estimate.

ScoutingScreen exposes direct inventory-use actions for `スカウト再調査` and `潜在能力鑑定`; purchasing remains in Shop.

---

## 14. Normal-training integration

`training-efficiency-boost` stays inside the existing authoritative normal training action:

1. detect pending boost;
2. pass the `120%` modifier into extracted/reused growth calculation before final integer rounding;
3. resolve normal training;
4. include `shop-training-boost` in public modifiers/logs;
5. clear pending effect;
6. commit training + effect consumption through the same game-operation transaction.

Validation or persistence failure keeps the effect pending.

---

## 15. PvP boundary

Never serialize into PvP/public PvP DTOs:

- inventory;
- purchase/use history;
- yearly counters;
- canonical shop operation rows;
- `shopEffects` / pending training boost;
- scouting insights;
- server item effect definitions.

Permanent base ability changes earned from a committed training camp, special coach, or boosted normal training may naturally affect a later PvP snapshot. The temporary item metadata never does.

---

## 16. UI

Existing five-tab navigation remains unchanged.

Path: `その他 → ショップ`.

Shop local views:

- `商品`;
- `所持品`.

Product card shows effect summary, annual usage, current-year quantity, `¥0`, and purchase/block state.

Inventory lists only current-year quantity > 0. It shows `今年度のみ有効`.

Target flows:

- fatigue recovery: eligible players sorted by fatigue descending;
- special coach: player then focus;
- scout research/appraisal: direct from scouting candidate card;
- extra candidate/training camp/training boost: confirmation panel.

Results show actual before/after or summary data, not only `使用しました`.

Training boost shows persistent badge `次回練習 成長効率 +20%` until consumed.

---

## 17. Loading/retry/unknown result

Catalog uses local loading/error UI while navigation remains visible.

During purchase/use, only the active operation is disabled.

If the network fails after submission, do not claim failure. Show an unknown-result state and allow same-`operationId` retry/status reload.

Revision conflict shows a clear `最新状態を読み込む` action and never silently overwrites newer data.

## 20. Completion criteria

Phase 5 is complete only when:

- all seven items exist and all prices are `¥0`;
- no real-payment code exists;
- purchase/use are server authoritative;
- annual limits and year expiration are server enforced;
- one canonical shop operation ledger guarantees global per-user idempotency;
- revision conflicts are safe/visible;
- inventory + GameState + counters + histories + scouting mutations are atomic where relevant;
- scouting hidden truth remains server-only and report refresh cannot reroll estimates;
- training boost consumes exactly once only on successful normal training;
- transient shop metadata never enters PvP snapshot/public DTOs;
- loading/success/error/unknown-result states are visible;
- 320/360/390/480px layout audit remains green;
- required unit/integration/E2E tests pass;
- `npm run verify` passes;
- `npm run test:e2e` passes;
- final diff review finds no browser direct-write path to authoritative shop tables and no duplicate production item-effect write path.

The implementation PR remains Draft/unmerged until stacked Phase 3/Phase 4 integration is resolved and merge is explicitly authorized.
